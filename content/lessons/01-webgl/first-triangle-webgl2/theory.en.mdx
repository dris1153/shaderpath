## From Three Loose Pieces to a Real Triangle

The last three lessons left exactly three loose pieces: a buffer holding vertex data (VBO/VAO), a vertex/fragment shader pair that knows how to read attributes/uniforms/varyings, and the concept of rasterization turning a triangle into fragments. This lesson wires all three into one working component — the demo below (`demo.tsx` alongside `triangle.vert`/`triangle.frag`) — in exactly the order you'll repeat in EVERY raw WebGL2 program from here on: compile → link → load data → draw. None of those four steps is optional; skipping the error-check at any one of them never raises a JavaScript exception — it produces a blank canvas instead, which is why most of this lesson is about HOW TO CATCH failures, not just how to call the API correctly.

## Compiling Shaders: #version 300 es and the Error-Check Pattern

The very first line of both `triangle.vert` and `triangle.frag` has to be `#version 300 es` — no whitespace or comment allowed before it; GLSL ES 3.00 requires that directive on line 1 exactly, or the compiler treats the shader as ES 1.00 and the `in`/`out` keywords (replacing the older `attribute`/`varying`) throw a syntax error. The demo's `compile()` helper does exactly four things: `gl.createShader(type)` requests an empty shader object, `gl.shaderSource(shader, source)` loads the GLSL text into it, `gl.compileShader(shader)` asks the driver to compile it — and this is the single easiest step to skip: `compileShader` never throws an exception no matter how broken the GLSL is, it silently sets an internal flag instead. The only way to know whether compilation succeeded is to ask explicitly with `gl.getShaderParameter(shader, gl.COMPILE_STATUS)`; on failure, `gl.getShaderInfoLog(shader)` returns an error string with real line numbers into the source you just loaded, including a misplaced `#version` line.

## Linking the Program: Joining Two Shaders, Checking LINK_STATUS

A single shader can't do anything on its own — `gl.createProgram()` creates an empty program, `gl.attachShader` attaches both the successfully compiled vertex and fragment shaders to it, and `gl.linkProgram(program)` matches the `out`/`in` variables between the two stages by name (exactly the varying mechanism from the previous lesson) and assigns storage locations to every attribute and uniform. Linking can fail too — even when both shaders compiled individually — for instance an `out vec3 vColor` in the vertex shader whose type doesn't match `in vec3 vColor` in the fragment shader — so `gl.getProgramParameter(program, gl.LINK_STATUS)` and `gl.getProgramInfoLog(program)` form the exact same mandatory check pair as compilation above. Once linking succeeds, the original shader objects aren't needed anymore — the demo calls `gl.deleteShader(vs)`/`gl.deleteShader(fs)` right away; the GPU keeps the compiled code alive inside `program` through reference counting.

## One Interleaved VBO + VAO, Two Attributes

The demo uses exactly ONE buffer holding both position and color interleaved: each vertex is 5 floats (`x, y, r, g, b`), 20 bytes total (5 × 4 bytes). `gl.bindVertexArray(vao)` runs first, then `gl.bufferData` uploads the whole `Float32Array` to the GPU in one call — not a separate buffer per attribute, one interleaved buffer. Two different `vertexAttribPointer` calls read from that SAME buffer at different offsets: `aPosition` reads 2 numbers starting at byte 0, `aColor` reads 3 numbers starting at byte 8 (after the first 2), and both use a stride of 20 to jump to the next vertex correctly. This entire configuration — two `vertexAttribPointer` calls, two `enableVertexAttribArray` calls, plus the currently bound buffer — is fully captured by the VAO; from now on a single `gl.bindVertexArray(vao)` before drawing is enough, with no need to repeat those four setup calls every frame.

## The Draw Loop: viewport, clear, useProgram, bindVertexArray, drawArrays

The loop inside `useVisibleRaf` runs exactly five steps every frame, and the order matters. `gl.viewport(0, 0, w, h)` has to run again whenever the canvas's size changes — the viewport does NOT automatically track the drawing buffer's size, and forgetting this step after a resize draws correctly but at the wrong scale or in the wrong corner. `gl.clear(gl.COLOR_BUFFER_BIT)` wipes the default framebuffer (the canvas itself) to whatever color `clearColor` set. `gl.useProgram` only needs to run again if you switch to a different program — this demo has exactly one program, so it's called once at setup, and WebGL keeps that "currently active program" state until you explicitly change it. `gl.bindVertexArray(vao)` restores the entire attribute configuration captured in the previous step. Finally `gl.drawArrays(gl.TRIANGLES, 0, 3)` fires the actual draw command: mode `TRIANGLES` groups every 3 consecutive vertices into one triangle, offset `0` starts at the buffer's first vertex, count `3` means read exactly 3 vertices. This is precisely where the pipeline hands off from your JavaScript to fixed-function hardware: `drawArrays` triggers the vertex shader to run 3 times (vertex specification → vertex shader), the GPU automatically groups the 3 vertices into a primitive and clips it into clip space (primitive assembly → clipping), the rasterizer generates fragments and interpolates `vColor` per fragment (rasterization), the fragment shader runs independently for each fragment (fragment shader) and writes color straight into the default framebuffer — this demo enables neither depth testing nor blending, so it skips the depth/stencil/blend stage entirely, and the fragment color goes straight to the canvas.

## ~40 Lines of Ceremony: A Mental Template You'll Reuse Forever

Strip away the JSX, the bilingual labels and the React plumbing, and the actual core of WebGL API calls in the demo — compile, link, buffer/VAO, draw loop — adds up to roughly 40 lines (an estimate, counting only the `gl.*` calls). What's worth memorizing isn't each individual line, but the three-phase skeleton: **Setup** (get the context → compile 2 shaders → create the program, attach, link, check status) → **Data** (create a buffer, upload data, create a VAO, configure attributes) → **Draw** (viewport → clear → useProgram if needed → bindVertexArray → set uniforms → drawArrays). Every raw WebGL2 program from here through the rest of Track 1 — textures, framebuffers, depth testing — fits neatly into these same three phases, only adding a step in the middle (bind a texture, configure an FBO...), never changing the skeleton itself.

<Callout variant="mistake" title="Common mistakes">

The three most common reasons a canvas shows only the clear color, no triangle:

1. Silent shader compile failure. `compileShader`/`linkProgram` never throw an exception no matter how broken the GLSL is — skipping the `COMPILE_STATUS`/`LINK_STATUS` check pair (or ignoring the error log) leaves the program "running" with an empty or broken shader; calling `useProgram` on a link-failed program raises an internal GL error rather than a JS exception, and the following `drawArrays` draws nothing valid.
2. A 0×0 viewport. `gl.viewport` never re-runs automatically when the canvas resizes — calling it before the canvas has a real size (say, before its container has finished laying out) or forgetting to call it again after a resize leaves the GPU rasterizing into a 0-pixel region: the draw call still "succeeds," it just produces 0 fragments.
3. The wrong attribute location. `gl.getAttribLocation` returns `-1` for a name that doesn't exactly match the shader (a typo, or an attribute the compiler stripped from the linked program because it never affects `gl_Position`) — calling `enableVertexAttribArray(-1)` is a silent no-op, position data never reaches the vertex shader, `gl_Position` stays at its default for every vertex, and the "triangle" collapses to a single point.

</Callout>
