## The GPU Can't Read JavaScript Arrays

A JavaScript `number[]` or object literal lives on V8's managed heap — garbage-collected, each element possibly a boxed small integer or a pointer to another object, and the language spec never guarantees a contiguous memory layout. A GPU wants the opposite: one contiguous, fixed-size block of bytes it can copy straight into VRAM and index with plain address arithmetic — no room for pointers or boxing. `gl.bufferData(gl.ARRAY_BUFFER, data, usage)` is exactly that copy: it takes a `BufferSource` — in practice always a TypedArray — and copies its raw bytes into a buffer living in GPU-accessible memory (a VBO, Vertex Buffer Object, the classic OpenGL nickname the WebGL community still uses even though the spec just calls it "a buffer bound to ARRAY_BUFFER"). Before that copy runs, the GPU has no idea your vertex data even exists.

Concretely, three separate steps are involved: `gl.createBuffer()` only allocates an empty handle (like a file descriptor with zero bytes behind it); `gl.bindBuffer(gl.ARRAY_BUFFER, buffer)` makes that handle the "current target" of the `ARRAY_BUFFER` binding point — WebGL is a state machine, so subsequent calls act on whatever is currently bound, not on an id you pass directly; `gl.bufferData(...)` is the call that actually copies bytes. The most common beginner mix-up is treating "creating a buffer" and "filling a buffer" as one step — they're three separate calls with three separate jobs.

## Float32Array and Byte Layout

WebGL vertex data is almost always `Float32Array` — a typed array of IEEE-754 32-bit floats, 4 bytes each, packed with zero padding between elements. `new Float32Array([1, 2, 3])` allocates exactly 12 bytes: element 0 sits at byte 0, element 1 at byte 4, element 2 at byte 8. That fixed, predictable layout is exactly what lets a GPU read it with pure address arithmetic — no need to chase a length field or follow a pointer. It's precisely the property a plain `number[]` lacks: its underlying memory shape isn't part of the language spec, which is why `bufferData` refuses it outright — it has to go through a TypedArray first.

## Interleaved vs Separate Attribute Buffers

A vertex usually needs more than one attribute: position, color, normal, UV. There are two ways to lay several attributes into buffers: **interleaved** — one single buffer, every vertex's fields packed back-to-back (`x,y,r,g,b, x,y,r,g,b, ...`) — or **separate** — one independent buffer per attribute (all positions in one `Float32Array`, all colors in another). Interleaved wins on cache behavior: reading one vertex's position and color touches a single contiguous byte region instead of two separate fetches into two different buffers — with a mesh of hundreds of thousands of vertices, that difference shows up as real, measurable cache-line traffic. Separate buffers win on flexibility: updating only positions (skinning, particle simulation) means touching one small buffer, never the color bytes that didn't need to change.

### Worked Example: 20-Byte Stride

Take the exact layout this track reuses throughout: 2 floats for position ($x, y$), 3 floats for color ($r, g, b$) — 5 floats total, 4 bytes each, **20 bytes per vertex**. For vertex index $i$, its data starts at byte $i \times 20$. Inside that 20-byte block: position occupies bytes $[0, 8)$ (2 floats × 4 bytes), color occupies bytes $[8, 20)$ (3 floats × 4 bytes). `gl.vertexAttribPointer(aPosition, 2, gl.FLOAT, false, 20, 0)` tells the GPU: read 2 floats, stride 20 bytes between consecutive vertices, starting at byte offset 0. `gl.vertexAttribPointer(aColor, 3, gl.FLOAT, false, 20, 8)` reads 3 floats, the same 20-byte stride, but starting at byte 8. Get either the `20` or the `8` wrong by even 4 bytes — one float's worth — and the GPU reads the wrong bytes as color: no crash, just silently wrong pixels, which is exactly what the demo below lets you break on purpose to see.

## The VAO: a Recorded Wiring Table for Attribute Pointers

A Vertex Array Object doesn't hold vertex data — it holds **state**: which buffer is bound to which attribute, the stride, offset, type and component count of every `vertexAttribPointer` call, and which attributes are enabled. Call `gl.bindVertexArray(vao)` once, run through the `bindBuffer` / `vertexAttribPointer` / `enableVertexAttribArray` sequence, and that entire wiring gets recorded onto `vao`. The next frame — or the next draw call for a completely different mesh — a single `gl.bindVertexArray(vao)` instantly restores every one of those pointer settings; the GPU isn't re-parsing anything, it's just switching to a pre-recorded wiring table. Without a VAO (WebGL2 always provisions one, mandatory rather than optional the way WebGL1 treated it), you'd have to repeat the full `vertexAttribPointer`/`enableVertexAttribArray` sequence before every single draw call — slower, since the driver re-validates everything, and error-prone, since forgetting to re-enable one attribute leaves it silently reading attribute 0's constant value instead of the buffer. A scene with 50 different meshes is 50 VAOs, each remembering its own wiring — switching meshes becomes 50 cheap `bindVertexArray` calls, not 50 × N pointer calls.

## STATIC_DRAW vs DYNAMIC_DRAW: Usage Intent

`bufferData`'s third argument — `gl.STATIC_DRAW`, `gl.DYNAMIC_DRAW`, or `gl.STREAM_DRAW` — isn't a hard constraint; WebGL will happily let you re-upload to a `STATIC_DRAW` buffer every single frame if you insist. It's a **hint** the driver uses to decide where to physically place the buffer in memory. `STATIC_DRAW` promises "written once, drawn many times" — right for geometry that never changes after load, freeing the driver to place it in the fastest, most GPU-local memory available. `DYNAMIC_DRAW` promises "written repeatedly, drawn many times between writes" — the driver instead picks a location that tolerates frequent CPU writes without forcing a full GPU stall. Lying to the driver — `STATIC_DRAW` on a buffer you re-upload every frame — doesn't break correctness, only performance, because every re-upload can trigger a slow memory migration the hint was supposed to prevent in the first place.

## Demystifying bindBuffer → bufferData → vertexAttribPointer → enableVertexAttribArray

The four-call sequence that opens nearly every WebGL setup reads confusingly out of order — until you name exactly what each call configures: `bindBuffer` selects **which** buffer subsequent calls act on (a state-machine "current selection," not a direct parameter); `bufferData` copies a typed array's bytes into that selected buffer; `vertexAttribPointer` tells the GPU **how to read** those bytes for one specific attribute — but only takes effect once `enableVertexAttribArray` flips that attribute from "constant value" mode into "read from buffer" mode. Skip the `enable` call and the pointer setup is silently ignored — the attribute keeps whatever constant (usually all zeros) was last set with `vertexAttrib*`, and the geometry vanishes without a single line printed to the console.

The next lesson — Vertex Shader, Fragment Shader & Rasterization — is exactly where the VBO this lesson just built gets read: `aPosition` and `aColor` become the `in` variables a vertex shader receives once per vertex, pulled straight from the wiring a VAO just recorded. <Callout variant="mistake" title="Common mistakes">

The three most common VBO/VAO mistakes:

1. **Forgetting to call `enableVertexAttribArray`.** `vertexAttribPointer` was called correctly, but the attribute still reads a constant value instead of the buffer — geometry vanishes with zero errors in the console, because nothing about it is technically invalid.
2. **Miscomputing stride/offset in bytes with multiple interleaved attributes.** Forgetting that 3 color floats take up 12 bytes (not 3) when computing the next attribute's offset — being off by even 4 bytes is enough for the GPU to read the wrong field's data.
3. **Assuming a VAO remembers "which buffer is currently bound to ARRAY_BUFFER."** A VAO doesn't store that global binding point — it stores which buffer was bound **at the exact moment** each `vertexAttribPointer` call ran, per attribute. Binding a different buffer afterward doesn't retroactively update the VAO; this is exactly why you can safely bind a different buffer for something else in between without corrupting the VAO's recorded config.
