## mat2/mat3 in GLSL: Constructors Read by Column

GLSL ships `mat2`, `mat3` and `mat4` as built-in types, and the way you construct them is the single most error-prone step when you start writing transform shaders. `mat2(a, b, c, d)` does **not** fill values row by row the way you'd write a matrix on paper — it fills by **column**: the first two arguments become column 0, the next two become column 1. This is exactly the column-major convention the Track 0 Matrices 2x2 & 3x3 lesson stressed: read a matrix column by column, because each column is where a basis vector lands after the transform — column 0 is where $(1,0)$ goes, column 1 is where $(0,1)$ goes.

The standard rotation matrix (counter-clockwise, X pointing right, Y pointing up) looks like this on paper:

$$
R(\theta) = \begin{pmatrix} \cos\theta & -\sin\theta \\ \sin\theta & \cos\theta \end{pmatrix}
$$

Column 0 of $R(\theta)$ is $(\cos\theta, \sin\theta)$, column 1 is $(-\sin\theta, \cos\theta)$. The correct GLSL constructor is:

```glsl
mat2 rotate2d(float angle) {
  float c = cos(angle);
  float s = sin(angle);
  // column-major: column 0 = (c, s), column 1 = (-s, c)
  return mat2(c, s, -s, c);
}
```

This is the most common shader-matrix bug there is: people read a matrix on paper in row order (left to right, top to bottom) and type those same four numbers straight into `mat2(...)`. For $R(\theta)$, the row order is $\cos\theta, -\sin\theta, \sin\theta, \cos\theta$ — typing that sequence directly into the constructor produces `mat2(c, -s, s, c)`, and since GLSL reads by column, the actual result is column 0 $= (c, -s)$, column 1 $= (s, c)$ — exactly $R(-\theta)$, the **inverse** of the matrix you meant to build. The shape rotates by the right amount but in the wrong direction, and this bug is nearly invisible just by staring at the output unless you know exactly what to look for.

## Rotating UV Space: Transform the COORDINATE, Not the "Image"

A fragment shader has no notion of an "image" to rotate — it only has a UV coordinate per pixel and a formula that decides that pixel's color. To make a pattern *look* like it's spinning, you don't rotate the pattern — you rotate the UV coordinate before feeding it into the pattern formula, and the pattern automatically holds still inside that new coordinate frame.

The direct consequence: whichever way you rotate the coordinate, the pattern you *see* appears to spin the **opposite** way. Picture standing still and turning a camera clockwise — the world in frame appears to spin counter-clockwise around you. Applied to code: multiply UV by $R(\theta)$ (rotating the axis frame $\theta$ degrees counter-clockwise), and the sample point moves counter-clockwise through the pattern's own space — so the pattern rendered on screen appears to rotate **clockwise** instead. This is the "inverse-transform intuition": you're not moving the pattern, you're moving the sample point backwards relative to a pattern that never moves.

```glsl
vec2 p = rotate2d(angle) * uv; // rotate the COORDINATE by +angle
// → the visible pattern appears to rotate by -angle on screen
```

## Pivot: Rotating Around Any Point, Not Just the Origin

`rotate2d(angle) * uv` rotates around the origin $(0,0)$ — with UV running over $[0,1]$, that origin sits at the bottom-left corner, not the pattern's center. The result: the whole pattern swings around a screen corner instead of spinning in place. The fix is exactly three steps — translate the point to the origin, apply the matrix, translate it back:

$$
p' = M\,(p - c) + c
$$

where $c$ is the pivot point (usually $(0.5, 0.5)$, UV space's geometric center):

```glsl
vec2 p = uv - pivot;   // translate → origin
p = rotate2d(angle) * p; // transform
p += pivot;              // translate back
```

Skipping this translation step is the usual reason a "spin in place" effect instead looks like it's "orbiting" a screen corner — two visually different symptoms that share exactly one root cause: two missing lines of translation.

## Time-Driven Rotation: Matrices That Live on uTime

The `angle` variable doesn't have to be a constant or a slider-controlled value — feeding it `uTime * speed` turns the rotation matrix into something *alive*, recomputed every frame. Since `rotate2d()` costs exactly one `cos()` and one `sin()`, that's far cheaper than a single texture sample, even running millions of times per frame (a rough estimate: a 1920×1080 screen at DPR 2 is around 8 million fragment invocations, each calling `rotate2d()` once if it sits inside `main()`). The thing to watch isn't the cost itself, but *where* the matrix sits: if `rotate2d()` ends up inside a large loop (raymarching, domain repetition — a Track 8 topic), that cost compounds with every iteration and stops being "cheap."

## mat3 and Homogeneous Coordinates: Folding Rotate + Translate Into One

`mat2` can only represent linear transforms (rotate, scale, shear) — translation isn't linear, so it can't be folded into a `mat2`, which is exactly why the translate→transform→translate-back technique above needed three separate lines. The Track 0 Homogeneous Coordinates & 4x4 Matrices lesson introduced the trick of adding a $w$ component to fold translation into matrix multiplication; the 2D equivalent uses `mat3` with $w = 1$ for points:

$$
\begin{pmatrix} x' \\ y' \\ 1 \end{pmatrix} = \begin{pmatrix} \cos\theta & -\sin\theta & t_x \\ \sin\theta & \cos\theta & t_y \\ 0 & 0 & 1 \end{pmatrix} \begin{pmatrix} x \\ y \\ 1 \end{pmatrix}
$$

```glsl
mat3 build2DTransform(float angle, vec2 translate) {
  float c = cos(angle);
  float s = sin(angle);
  return mat3(
    c, s, 0.0,               // column 0
    -s, c, 0.0,               // column 1
    translate.x, translate.y, 1.0 // column 2
  );
}

vec2 applyTransform(mat3 m, vec2 p) {
  return (m * vec3(p, 1.0)).xy; // append w=1, multiply, drop w
}
```

One `mat3` multiply can package the whole translate-transform-translate-back chain (note: `build2DTransform(angle, translate)` by itself is "rotate about the origin, then translate" — for it to equal a rotation about pivot $c$, pass $t = c - R\,c$) — useful once you need to compose several transforms in sequence (rotate, then translate, then rotate again) without stacking rounding error or re-writing the same translation boilerplate at every step.

This technique doesn't stop at GLSL: Track 4 (React Three Fiber): when you set `mesh.position`/`rotation`/`scale`, Three.js's `Object3D.updateMatrix()` builds the model matrix as the T·R·S composition (right-to-left: scale → rotate → translate) about the object's local origin — this lesson's pivot trick is what you reproduce in three by nesting the mesh inside a group placed at the pivot. Track 8 (Raymarching) reuses the same translate-transform-translate-back trick to repeat a shape infinitely with O(1) memory in domain repetition, and Track 6 (Custom Shaders) lets you inject these `mat3`/`mat4` matrices directly into Three's built-in pipeline via `onBeforeCompile`.

<Callout variant="mistake" title="Common mistakes">

The three most common mistakes when transforming UV with matrices:

1. **Typing a matrix's row order into a column-major constructor.** `mat2(a,b,c,d)` fills column 0 $=(a,b)$, column 1 $=(c,d)$ — typing $R(\theta)$'s four numbers in the order you'd read them on paper produces $R(-\theta)$, rotating by the right amount in the wrong direction, and it's nearly impossible to spot just from the output.
2. **Forgetting to translate to the pivot before rotating.** `M * uv` rotates around the origin $(0,0)$ (UV's bottom-left corner), not the pattern's center — skipping `uv - pivot` before and `+ pivot` after makes the shape swing around a screen corner instead of spinning in place.
3. **Confusing the coordinate's rotation direction with the visible pattern's rotation direction.** Rotating UV by $+\theta$ makes the rendered pattern appear to rotate by $-\theta$ — forgetting this inverse relationship makes an animation spin "the wrong way" compared to the design, even though the math itself is correct.

</Callout>
