## Three Tool Classes, Three Programming Models

CSS, Framer Motion/Motion, and GSAP don't really compete head-to-head, despite first impressions — each solves animation at a different layer: CSS is a native browser capability, Motion is welded to React's component model, and GSAP is a framework-independent JS library operating directly on the DOM. Knowing the layer matters more than memorizing the API — API details are a doc lookup away; picking the wrong layer means every line afterward points the wrong direction.

### CSS Animations & Transitions: Declarative, Compositor-Friendly, Zero JS Cost

CSS animation/transition is pure declaration: describe a start/end state or keyframes, the browser interpolates, and JS at most toggles a class. The price of "no JS needed" is speed: transform and opacity — the only properties cheap enough to animate unconditionally — run on the compositor thread, isolated from the main thread, staying smooth even while it's busy (the compositor-friendly-animation lesson later in this module explains why). That makes CSS the correct default for every hover, focus, and active state.

The real limits start with coordination: `animation-delay` fakes a short sequence, but past three or four interdependent elements, hand-managing delays stops being maintainable. CSS also has no "progress driven by a runtime value" — tying an animation to mouse position or real scroll percentage means rewriting a custom property in JS every frame, at which point CSS is just a display layer.

```css
.card {
  transition: transform 150ms ease-out, box-shadow 150ms ease-out;
}
.card:hover { transform: translateY(-4px); }
.card:active { transform: scale(0.95); transition-duration: 75ms; }
```

### Framer Motion / Motion: React-Idiomatic Layout and Gesture Animation

Motion (Framer Motion's name since 2025) speaks React's own language: `<motion.div>` with an `animate` prop, `whileHover`/`whileTap` instead of hand-wiring `addEventListener`, and `<AnimatePresence>` that animates a component out during unmount — something plain CSS/JS can't do cleanly, since React removes the node before an exit animation gets a chance. Its standout feature is layout animation: a `layout` prop makes Motion measure position/size before and after a layout change and smoothly animate between them — FLIP under the hood, the same technique GSAP's Flip plugin (taught earlier in this track) exposes explicitly, except automatic here.

The limits: `useScroll` covers light parallax fine but has no separate pin/scrub/snap the way ScrollTrigger does. And nearly all its ergonomic advantage is tied to React — it works in Vue/vanilla too (`animate()` is framework-independent) but loses the component-aware part worth reaching for in the first place. This platform doesn't install Motion at all — no `import` of it appears in any demo; it's discussed here purely as a real option that exists.

### GSAP: Imperative Timelines and the ScrollTrigger Ecosystem

GSAP runs the opposite direction: fully imperative — call `gsap.to()`, `gsap.timeline()`, decide yourself when to play, pause, reverse, or jump with `.seek()`. That explicitness buys coordination power: a `timeline` sequences tweens by relative position, `stagger` fans delay across hundreds of elements, and ScrollTrigger (now entirely free) gives scrub/pin/snap deeper than anything else available — pin a section, lock its progress to exact scroll position, in a few config lines. GSAP doesn't care whether you're in React, Vue, or plain HTML — same API, fully portable.

The cost shows up elsewhere: the imperative style collides with React's declarative model. A tween created outside a managed lifecycle survives unmount, animating a node already removed from the DOM — or worse, one React reuses for something else. The required discipline: scope every tween inside `gsap.context()`, `.revert()` on unmount (the tweens-timelines-stagger and scrolltrigger-plus-r3f-single-loop lessons already drilled this) — skipping it isn't a syntax error, it's a silent leak that surfaces only after the app runs a while or remounts a few times.

## Four Axes for Choosing

1. **Choreography complexity** — one property, two states → CSS is enough. A component entering/exiting with a gesture → Motion. A five-or-six-element sequence with interdependent timing → a GSAP timeline.
2. **Scrub/scroll needs** — fires once on trigger → any of the three works. Must track scroll percentage exactly, or pin content → ScrollTrigger is the deepest tool available; Motion's `useScroll` covers light parallax; CSS scroll-driven animations (a newer spec, browser support still uneven at the time of writing — an estimate) suit simple effects with a fallback.
3. **Team/framework** — a React team doing component-scoped micro-interactions → Motion cuts boilerplate. Framework-agnostic, or animation living outside React's lifecycle → GSAP.
4. **Bundle cost** (estimated numbers, sourced from Bundlephobia — see references): Motion's trimmed `animate()` build runs ~2.6kB, full build ~18kB; GSAP's core is ~23.5kB. CSS costs 0kB of JS — its cost lives inside the browser engine already loaded.

## The Real Answer: Use All Three, Each Where It's Strongest

The right answer is rarely "pick one tool for the whole project" — it's the right tool per feature. A typical product landing page:

- A hero with an ordered text/logo entrance on load, then a section pinning itself on scroll to drive a product demo — exactly what GSAP + ScrollTrigger was built for.
- A pricing table with an expand toggle, a confirmation modal, a mobile nav drawer that slides in — component-scoped micro-interactions that need to animate out on unmount too — exactly where Motion shines.
- A button that lifts on hover, an underline sweep, an image that fades in once loaded — two states, no coordination, no React dependency — CSS transitions handle it in two lines.

No single project needs all three at once, but plenty are complex enough to benefit from all three — as long as the boundary stays clear, avoiding a heavy tool on a light job (mistake #1 below).

## Case Study: How Shaderpath Uses All Three

This platform illustrates the principle directly. Every Track 5 demo — including this one — uses GSAP deliberately, not because it's objectively "the best" but because the track's content IS GSAP, following the same "teach the real API" philosophy Track 1 applies with raw WebGL2 and Track 3 with vanilla Three.js. The platform's own UI, by contrast — buttons, lesson cards, nav hover effects — sticks to CSS transitions and Tailwind utilities, since those are simple two-state toggles; pulling in GSAP for a hover-lift would mean paying 23.5kB for something CSS already does free. Motion isn't in this project's `package.json` at all — not because it's bad, but because there's no layout-animation or React-gesture need large enough to justify the dependency.

## Where This Leads

Starting next lesson, "animation principles for UI" applies equally across all three tools — anticipation and follow-through aren't GSAP-exclusive. And no matter which tool you pick, the "animate only transform/opacity" rule from this module's closing compositor-friendly-animation lesson still holds — the tool only decides how you WRITE the animation; the compositor decides how fast it actually RUNS.

<Callout variant="mistake" title="Common mistakes">

The three most common animation-tool mistakes:

1. **Reaching for GSAP just to animate a hover state.** A `gsap.to(el, {y:-4})` on hover does exactly what two lines of CSS transition already do — for 23.5kB with zero real benefit. Default to CSS first; only upgrade to JS once the choreography outgrows what CSS can express.
2. **Creating a GSAP tween inside a React component without scoping it in `gsap.context()`.** The tween survives unmount and keeps animating a node that's already been removed from the DOM — or worse, one React has reused for different content after a re-render — producing a visual bug that only surfaces after repeated remounts (Strict Mode, route changes), not during a quick dev check.
3. **Treating Motion's layout animation as "free FLIP magic."** Every element with a `layout` prop gets measured with `getBoundingClientRect` on each layout change — fine for a few dozen elements, but a list of hundreds re-ordering every scroll frame turns that measurement into a real, accumulating cost, not a magic trick that costs nothing.

</Callout>
