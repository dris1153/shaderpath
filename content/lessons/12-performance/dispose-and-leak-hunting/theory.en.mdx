## The GC Illusion: JS Gets Collected, the GPU Doesn't

JavaScript's garbage collector is excellent at exactly one job: reclaiming JS objects with no more references. The catch is that a `THREE.Texture` is just a thin JS wrapper — the actual pixel data, once uploaded, lives in a `WebGLTexture` on the GPU driver side, entirely out of the GC's reach. Clear the `texture` variable, let it fall out of scope, even set `texture = null` — the GC will happily reclaim that JS object on its next pass, but the matching `WebGLTexture` on VRAM is **untouched**, because the GC has no idea it exists. The result is orphaned GPU memory: still alive, still occupying space, with no JS object left pointing at it to clean up. This kind of leak never shows up in `performance.memory` (which only measures the JS heap) — it only surfaces when the driver refuses to allocate more context, or the OS starts swapping. This is the most dangerous illusion when learning disposal: code that "looks clean" (no variable holds a reference anymore) does not mean the GPU is clean.

## The Dispose List

Four categories of object carry a `.dispose()` method and each allocate real GPU resources: **geometry** (vertex/index buffers), **material** (compiled shader program + state), **texture** — including every individual **map slot** attached to a material (`map`, `normalMap`, `roughnessMap`, `metalnessMap`, `aoMap`, `emissiveMap`, `alphaMap`, `envMap`, ... `MeshStandardMaterial` alone carries 11 distinct texture slots), **`WebGLRenderTarget`** (the FBO behind render-to-texture or a post-processing pass), and finally the **renderer** itself. The easiest thing to miss: `material.dispose()` does **not** cascade down to the textures attached to it — a material only knows how to free its own compiled shader program, never any map you assigned to it. A material using 4 maps (albedo, normal, roughness, AO) that only calls `material.dispose()` leaves all 4 textures sitting on VRAM untouched. A concrete number: a $512 \times 512$ RGBA8 texture (no mipmaps) occupies exactly $512 \times 512 \times 4 = 1{,}048{,}576$ bytes $= 1\text{ MiB}$ on the GPU; forgetting to dispose it across $n$ mounts accumulates orphaned VRAM linearly, $V(n) = n \times 1\text{ MiB}$ — 12 mounts alone is 12 MiB silently gone, and none of it shows up in `performance.memory`.

## What `dispose()` Actually Does

Reading Three.js's own source (version 0.185) directly: `BufferGeometry.dispose()`, `Texture.dispose()`, and `Material.dispose()` all do exactly one thing — `this.dispatchEvent({ type: 'dispose' })`. That call by itself touches nothing on the GPU. The real GPU cleanup lives inside `WebGLRenderer`'s internal managers (`WebGLGeometries`, `WebGLTextures`, ...): the first time an object gets rendered, its matching manager attaches a listener to that object's `'dispose'` event; when that listener fires, it calls the real `gl.deleteBuffer`/`gl.deleteTexture` and removes the entry from `WebGLProperties` — an internal `WeakMap` mapping each Three.js object to its GPU handle. The practical upshot: calling `dispose()` on an object that was **never rendered** is a safe no-op (there's no `__webglInit` to clean up); and if you keep using that same object after disposing it (setting `needsUpdate = true`, rendering again), Three simply re-uploads from scratch — dispose is cheap and safe to call even when you aren't sure the object ever reached the GPU. `renderer.dispose()` follows the same logic: it removes the context-lost listeners and wipes `WebGLProperties` plus its internal caches (program cache, render lists...) — but it does **not** destroy the context or the canvas; if you keep rendering afterward, the driver is still there, Three just has to rebuild its state from zero.

## What R3F Handles — and Exactly Where `useDisposable` Fills the Gap

R3F automatically calls `.dispose()` on any object **its own reconciler instantiated** from a JSX tag (`<boxGeometry />` → `new THREE.BoxGeometry()` lands on R3F's own books) once the component holding that tag unmounts; to opt out (geometry shared across multiple meshes), set `dispose={null}`. What's left uncovered — and in practice this is the biggest gap — is anything you `new THREE.X()` **outside** JSX and attach via `<primitive object={...} />`, build inside a `useEffect`/`useMemo`, or a `WebGLRenderTarget` you create by hand for a side pass: R3F never tracks these, so disposing them is on you.

This platform's `lib/hooks/use-disposable.ts` is the answer to exactly that gap. The API is deliberately thin: `register(obj)` pushes a Three.js-disposable into an internal array and hands it straight back (call it inline right where you `new` the object); `registerFn(fn)` accepts any cleanup callback for things without a `.dispose()` method (removing a listener, canceling a RAF). On unmount, `disposeAll()` runs `fns` first, then `objects` — both in **LIFO** order (last created, first disposed). That order isn't arbitrary: `fns` run first to stop any loop or listener still reading data, only then does GPU resource disposal happen — reversing that order risks a still-running callback reading a geometry that was just disposed out from under it. Each call is wrapped in its own `try/catch`, so one failing cleanup never blocks the rest. This is exactly the hook the demo below uses to tell the "clean" branch apart from the two "leaky" ones.

## Hunting Leaks for Real: `renderer.info` First, Heap Snapshots Second

The first, cheapest tool, always worth turning on before anything else: `renderer.info.memory.geometries`/`.textures` — the count of GPU resources **currently alive**, rising on creation, falling exactly when the `'dispose'` listener fires. A correct component should bring both numbers back to the same baseline after every mount/unmount cycle; testing once and calling it "fine" is the classic methodological mistake — leaks only reveal themselves across repeated cycles, and the same polling philosophy this platform's own e2e suite already relies on elsewhere (`data-frames` + `expect.poll` instead of a fixed `sleep`, spec §8.3) applies here identically: read the number continuously across many cycles, don't guess from a single snapshot.

Once the numbers confirm a leak, step two is Chrome DevTools → Memory tab → Heap Snapshot, in a three-step workflow: capture (baseline) → act (mount then unmount the suspect component a few times) → capture again. Switch the second snapshot to **Comparison** mode against the first — the "# Delta"/"Size Delta" column immediately exposes which constructor grew net across the cycles (type "Texture" or "BufferGeometry" into the class filter to narrow it down). Clicking a still-alive instance opens the **Retainers** tree below it — read it bottom-up: each row answers "who is holding a reference to this object", and walking that chain usually surfaces the real culprit (a closure, a module-level array, a cache `Map`) rather than the object itself.

## The Four Classic Leak Shapes

Beyond the obvious "forgot to call dispose," four shapes fool even careful engineers: **an event listener holding a scene reference** — `window.addEventListener('resize', () => scene.traverse(...))` never removed in cleanup keeps the entire `scene` alive through the closure; **a module-scope cache** — a `Map<string, THREE.Texture>` declared outside the component to "reuse" textures but never evicting stale entries; **a RAF loop surviving unmount** — calling `requestAnimationFrame` by hand outside `useFrame`/`useVisibleRaf` and forgetting `cancelAnimationFrame` in cleanup, exactly the bug this platform's `useVisibleRaf` was written to prevent (an `IntersectionObserver` starts/stops the RAF, and it always cancels once the container leaves the DOM); and **a closure inside a GSAP/ScrollTrigger callback** (Track 5) holding a mesh/material reference inside `onUpdate` without `revert()`-ing the timeline when the component unmounts.

<Callout variant="mistake" title="Common mistakes">

The three most common mistakes when disposing GPU resources:

1. **Disposing a material but forgetting each map slot attached to it.** `material.dispose()` doesn't cascade to `map`/`normalMap`/`roughnessMap`/... — each texture slot is its own object and needs its own `texture.dispose()`, even when the material "looks" cleaned up.
2. **Assuming `renderer.dispose()` destroys the context/canvas like `loseContext()` does.** It only clears internal caches (`WebGLProperties`, program cache) and removes the context-lost listeners — the WebGL context is still alive. Calling it in a child component's cleanup, when the parent `<Canvas>`/`DemoCanvas` already owns and manages the renderer's lifecycle, is redundant and can interfere with R3F's own dispose schedule.
3. **Concluding "no leak" after a single try.** `renderer.info.memory` only reveals a leak when compared across **multiple** mount/unmount cycles — a single mount/unmount almost always "looks fine" even when every cycle is silently accumulating a few objects.

</Callout>
