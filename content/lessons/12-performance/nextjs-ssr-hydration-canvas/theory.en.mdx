## The Server Has No WebGL — What That Actually Breaks

Next.js renders a page's first pass on the server (Node.js) and ships that HTML down for the browser to "hydrate." The server has no `window`, no real `<canvas>`, no GPU driver at all — so the real question isn't "does the WebGL canvas run on the server" (it doesn't need to), it's "does your code accidentally RUN something that touches a browser API while the server is rendering the component." Three concrete ways that happens: accessing `window`/`document` at **module scope** — `const dpr = window.devicePixelRatio` written outside any function runs the instant the module is imported, on both server and client, and on the server it throws a flat `ReferenceError: window is not defined`, taking down the whole request; calling `React.useLayoutEffect` inside a component that gets server-rendered — that effect never runs on the server (there's no "before paint" moment to speak of there), so React logs the dev warning "useLayoutEffect does nothing on the server"; and rendering content that depends on client-only state (like a `typeof window !== 'undefined'` branch directly in JSX) without going through a state/effect gate, which causes a hydration mismatch — React compares the server DOM against the client tree, finds them different, and has to throw the server DOM away and re-render from scratch on the client.

The good news: React Three Fiber's `<Canvas>` (verified directly against `@react-three/fiber@9.7`'s own source) is already SSR-safe by exactly this discipline. It renders a plain DOM tree — `<div><div><canvas /></div></div>` — touching no WebGL at all, and only creates the real `WebGLRenderer` inside `useIsomorphicLayoutEffect`, a helper that checks `typeof window !== 'undefined'` to pick `useLayoutEffect` on the client and `useEffect` on the server (running nothing at all during SSR). That's why the demos on this platform have never needed `ssr: false` to avoid crashing — they were already written to the exact discipline of "only touch WebGL/`window` inside an effect," the same discipline `use-disposable.ts`/`use-visible-frameloop.ts` follow.

## `next/dynamic` with `ssr: false` — the Standard Tool, and Where the Boundary Goes

So when do you actually need `next/dynamic(() => import('./Scene'), { ssr: false })`? When a library touches `window`/`document` right at module scope (not inside an effect) and you can't fix it, or when you deliberately want to skip the SSR pass entirely for a heavy component tree to save server CPU. Next.js's current docs (`node_modules/next/dist/docs/01-app/02-guides/lazy-loading.md`) confirm this plainly: by default, a Client Component is still **prerendered (SSR'd)** even when lazy-loaded through `next/dynamic`/`React.lazy` — `ssr: false` is the explicit opt-out. More important for the Next 16 App Router specifically: **`ssr: false` cannot be used directly inside a Server Component** — the docs say outright, "`ssr: false` is not supported in Server Components. You will see an error"; it's only valid called from inside a `"use client"` file. Putting the boundary in the right place means wrapping exactly the **canvas island** (the 3D component) with `next/dynamic`, not the whole page — text, headings, and SEO content stay in a Server Component so they get indexed and appear in the very first HTML.

## The Placeholder Strategy: Reserve Space Before It Shows Up

Whether the canvas mounts immediately or later, the space it will occupy has to be reserved **before** it appears — otherwise, content below jumps down the moment it mounts, a layout shift happening right in front of the user. This platform's `components/viz/demo.tsx` is a live example: every demo is wrapped in `<AspectRatio ratio={ratio}>` (locking a fixed aspect ratio regardless of whether the inner content has loaded yet) nesting a `<Suspense fallback={<Skeleton className="size-full" />}>` — the block's size is fixed by CSS straight from the server HTML, `Skeleton` fills the gap while the real `<Canvas>` hasn't mounted yet, and once it does, the block's height **doesn't change**, so nothing below it gets pushed.

## Suspense, Client-Side Lazy Loading, and Protecting FCP/LCP

`Suspense` + `React.lazy`/`next/dynamic` solve a different problem than `AspectRatio` — not "keep the layout stable" but "don't make the browser fetch and execute `three`/`drei` before there's anything to show." A heavy canvas should sit off the critical rendering path: defer mounting until it's **about to enter the viewport** (`IntersectionObserver`) or the browser is idle (`requestIdleCallback`), rather than mounting the instant the page loads. This platform's `useVisibleRaf`/`useVisibleFrameloop` were written for a different goal (pausing the RAF loop while the canvas is off-screen, spec §8.3), but they rely on exactly the `IntersectionObserver` mechanism a "mount when about to appear" strategy needs — the only difference is gating **mount** instead of gating the **frame loop**. The practical payoff: First Contentful Paint doesn't wait on `three` finishing its download, and Largest Contentful Paint (usually a heading or the page's opening text) never gets blocked behind 3D JavaScript.

## Bundle Discipline: `three`/`drei` Live in the Demo Chunk, Not the Page Chunk

`scripts/gen-lesson-registry.ts` generates `DEMO_REGISTRY`, a slug → `() => import("./lessons/.../demo")` map — each entry is its own dynamic `import()`, exactly what a bundler splits chunks around. The lesson page (`app/[locale]/lesson/[lessonSlug]/page.tsx`) is a Server Component that calls `await demoLoader()` directly instead of wrapping it in `next/dynamic` — worth being upfront about one thing here: Next's own docs note that when a Server Component dynamically imports a Client Component this way, automatic code-splitting isn't **guaranteed** the same way it is when the call happens from inside a Client Component via `next/dynamic`. This platform accepts that trade-off to keep demos prerendered (no Skeleton→Canvas flash even on a fast connection) rather than giving every demo its own `next/dynamic` wrapper. To measure this for real instead of guessing: `next experimental-analyze` (the Turbopack Bundle Analyzer, new in Next 16.1, and this project builds with Turbopack per `next.config.ts`) draws a per-route treemap and shows whether `three`/`@react-three/fiber` genuinely land in a separate demo chunk — the exact KB numbers have to be measured on the dev machine with that command, not guessed here.

## Hydration-Safe Patterns: the Mounted-State Gate, and Honest `suppressHydrationWarning`

The safest way to render content that differs between server and client: start from a value identical to the server's (`const [mounted, setMounted] = useState(false)`), flip it to `true` inside a `useEffect` (client-only), and only render the client-dependent content **after** `mounted === true` — the client's first render matches the server exactly, no mismatch, just a single frame of "flash" before the real content appears. `suppressHydrationWarning` is a different tool entirely: it tells React "accept whatever's in the DOM for this one element, don't warn" — reasonable when you **deliberately** put the correct value into the DOM some other way (an inline `<script>` that runs before React hydrates), wrong when it's used to silently paper over a mismatch you haven't actually understood. Don't reach for it because it makes the warning go away fastest; reach for the `mounted` gate when you can afford to wait a frame, and for `suppressHydrationWarning` only when you have another genuine source of truth for that DOM.

<Callout variant="mistake" title="Common mistakes">

The three most common mistakes when mixing WebGL canvases with Next.js SSR:

1. **Calling `next/dynamic(..., { ssr: false })` inside a Server Component.** Next 16 errors outright and refuses to build — `ssr: false` is only valid inside a `"use client"` file; to disable SSR for a canvas, create a Client Component wrapper and call `dynamic` from inside it.
2. **Reading `window.innerWidth`/`devicePixelRatio` at module scope** instead of inside an effect or callback — it works by accident on the client but crashes outright on the server, since `window` doesn't exist there, and testing only with `next dev` on a route that never got server-rendered may not surface it right away.
3. **Not reserving layout space for a canvas that's about to mount.** Missing a fixed `aspect-ratio`/size makes content below jump the instant `<Canvas>` appears — a UX failure on par with a pop-in ad shoving the page around.
